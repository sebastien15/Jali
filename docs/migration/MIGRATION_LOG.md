  - Persistence: minimal safe option = keep one global persisted entry and purge it on every session start and end (cancel queries → `queryClient.clear()` → `persister.removeClient()`); a throttled save after the clear can only write the empty cache. Added `buster: "jali-query-v1"` (schema version; existing un-bustered caches are discarded once on upgrade) and a dehydrate denylist `isSensitiveQueryKey`: all `rides` keys (detail/PIN, active, history, chat, estimates), hire detail (`["hire", <id>]`), `driver.onboarding`, `driver.profile`, and `admin.drivers*` (applications/documents). Per-user persister keys were not used: purge-on-change gives the same isolation with less code.
  - View state: `core/session/viewState.ts`, key `jali_view_state_v1:<userId>` (`{ driverMode, driverType }`), plus `jali_session_user_v1` (id of the account owning the stored token) so view state hydrates offline. The first read for an account with no entry migrates the legacy global `jali_driver_mode` once (copy, then remove): read-only defaults, never written to the server. Before `/me` is known (no cached id), the legacy value is displayed read-only. Server restore kept: if the account has no stored `driverType` and has a driver permission, `GET /driver/profile` services choose a default view type (read only).
  - Teardown clears all `jali_view_state_v1:*` keys, the legacy key and `jali_session_user_v1` (runbook §5.5 lists view state in teardown). Device preferences (`jali_language`, FX currency, recent places) are not cleared; admin web logout now restores `jali_language` after its `localStorage.clear()`.
